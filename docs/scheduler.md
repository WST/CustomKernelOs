# Планировщик

MyOS использует MLFQ: три FIFO-очереди готовых задач на каждом CPU.
Уровни: 0 — интерактивный, 1 — обычный, 2 — фоновый. Кванты равны
10/20/40 мс, суммарные бюджеты до понижения — 20/40/80 мс.
Исчерпание бюджета понижает приоритет; на нижнем уровне бюджет обновляется.
`yield` не обновляет оставшийся квант и накопленный бюджет.
Новые задачи начинают с уровня 1; потомки вычислительных пользовательских
задач наследуют их уровень и использованный бюджет, чтобы `fork` не давал
новый высокий приоритет. Учёт времени дискретный, с шагом 10 мс.

Ожидание от 20 мс повышает задачу до уровня 0. Для вычислительных всплесков,
которые длиннее ожидания, повышение ограничено одним разом в 200 мс.
Если предыдущая работа на CPU не длиннее ожидания, задача может повышаться
при каждом пробуждении.
После ожидания от 100 мс повышение происходит независимо от этого интервала.
Пробуждение уведомляет назначенный CPU через IPI; более высокий приоритет
может вытеснить текущую задачу. READY-задачи, ожидающие секунду, повышаются
на один уровень. Это предотвращает постоянное голодание фоновых задач.

Новые пользовательские задачи назначаются по числу готовых и работающих задач.
Простаивающий CPU может забрать готовую задачу; каждые 100 мс балансировка
переносит одну задачу при разнице загрузки больше единицы. Перенос разрешён
только для неактивного сохранённого ring-3 контекста: без системного вызова,
удерживаемого mutex и ожидающего завершения. FPU сохраняется перед тем,
как другой CPU сможет выбрать задачу. Потоки ядра остаются на CPU 0.
Очереди защищены существующей общей блокировкой ядра; ядро остаётся
сериализованным. Полного real-time поведения и CPU affinity API пока нет.

## Диагностика

`schedstat` показывает для каждого CPU текущую задачу, приоритет, длины
трёх очередей, переключения, миграции и среднее/максимальное ожидание.
Статистика накопительная с загрузки, счётчики 32-битные и могут переполниться.
Среднее округляется до целого тика. Приоритет 3 означает idle.

`schedinfo(out, capacity)` возвращает число CPU или отрицательную ошибку.
Ёмкость должна вмещать все CPU; снимок согласован под блокировкой ядра.
Заголовок `scheduler.h` также содержит гистограмму ожиданий: верхние границы
0/1/2/4/8/16/32 тика и последняя корзина для больших значений.
Номер нового системного вызова — 90; предыдущие номера сохранены.

## Проверки

```
make schedpolicytest
make schedtest
make smptest
make parallel-buildtest
```

Тест политики проверяет FIFO, бюджеты при yield, повышение после ожидания,
aging, размещение, ограничения миграции и целостность очередей. `schedtest`
использует временные диски без пользовательских настроек и проверяет
пробуждение под нагрузкой 12 CPU/FPU-процессов, ABI статистики, pthread и
согласованность перетаскиваемых окон на 1/2/4/8 CPU. Результаты сохраняются
в `build/scheduler-mlfq-*.log`. Основной `disk.img` не изменяется.

В сравнительном запуске QEMU дополнительная задержка после `sleep_ms(30)`
при 12 вычислительных процессах составляла 210 мс с прежним round robin
на одном CPU. С MLFQ на 1/2/4/8 CPU измерена задержка ниже шага таймера
10 мс. Это результат микротеста; он не является измерением FPS рабочего
стола или гарантией задержки на реальном оборудовании.
