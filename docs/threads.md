# Пользовательские потоки

Пользовательская программа может создавать несколько потоков и выполнять их
параллельно на доступных CPU (до 8). Процессорное время между готовыми задачами
одного CPU распределяет существующий вытесняющий round-robin планировщик:
квант — 20 мс. Потоки не обязаны вызывать `yield`, чтобы дать работать остальным.
Общий лимит увеличен до 256 задач, включая процессы, потоки и служебные задачи.

`threads` запускает 100 вычислительных потоков на 3 секунды; `threads 8` — восемь.
Число итераций зависит от нагрузки и CPU, поэтому не обязано совпадать.
Новые пользовательские задачи распределяются по CPU по кругу. Уже запущенные задачи не мигрируют. Гарантии точного равенства времени
между всеми CPU, приоритетов и сроков выполнения нет.

## API в myos.h

```c
int thread_create(void (*fn)(void *), void *arg, void *stack, unsigned size);
int thread_join(int tid, int *exit_code);
void thread_exit(int exit_code);
int gettid(void);
typedef struct { unsigned owner; } thread_mutex_t;
int thread_mutex_lock(thread_mutex_t *m);
int thread_mutex_unlock(thread_mutex_t *m);
```

`thread_create` возвращает положительный TID или отрицательный errno. Стек
выделяет вызывающая программа: доступный на запись непрерывный диапазон от
12 КиБ до 1 МиБ. Рекомендуется 64 КиБ. Его нельзя менять или освобождать до
успешного `thread_join`. Первая полная страница внутри буфера становится защитной; полезный стек уменьшается
на 4–8 КиБ. После join доступ восстанавливается. См. [изоляцию и стеки](isolation.md). `arg` передаётся
в `fn`; возврат из `fn` соответствует `thread_exit(0)`.

`thread_join` ждёт поток своего процесса, возвращает 0 и при ненулевом указателе
записывает код завершения. Повторный join возвращает `-ESRCH`; ожидание себя
или уже ожидаемого другим потоком TID — `-EBUSY`. Завершившийся поток занимает
слот до join или завершения процесса. У этого вызова отсоединённых потоков нет:
`pthread_detach` помечает поток, и ядро само снимает его mmap-стек.

Потоки разделяют адресное пространство, кучу, SHM-отображения, таблицу файловых
дескрипторов, текущий каталог и учётные данные. `getpid` возвращает общий PID,
`gettid` — ID текущего потока. Стек ядра, регистры, x87 FPU и состояние ожидания
у каждого потока свои. Файловый объект удерживается до окончания системного
вызова, даже если другой поток закрыл его дескриптор.

`exit`, завершение главного потока, `kill` PID/TID и ошибка памяти завершают
процесс с его потоками. Память процесса освобождается после остановки всех CPU,
которые её используют. `thread_exit` рабочего потока завершает только его.
`fork` и `exec` возвращают `-EBUSY`, пока есть неубранные потоки; рабочий поток
также не может выполнять эти операции. Для запуска другой программы из потока
доступен `spawn`.

Мьютекс нужно инициализировать нулём. Он нерекурсивный, при занятом мьютексе
поток блокируется в ядре. Lock/unlock возвращают 0 или отрицательный errno.
Снимать блокировку может её владелец. Завершение потока с захваченным мьютексом
не освобождает его автоматически. Для общих данных используйте мьютексы;
`volatile` сам по себе не делает операции атомарными. Аллокатор `malloc/free`
защищён внутренним мьютексом. `errno` у каждого потока свой: libc держит его
в пользовательском блоке, а ядро хранит указатель на этот блок. Остальная libc
по-прежнему без полной потоковой безопасности. Это собственный API MyOS;
POSIX-обёртка — `libpthread`.

```c
#include "myos.h"
static thread_mutex_t mutex;  /* нулевая инициализация */
static unsigned result;
static void work(void *arg) {
    thread_mutex_lock(&mutex);
    result += (unsigned)arg;
    thread_mutex_unlock(&mutex);
}
int main(void) {
    void *stack = malloc(65536);
    if (!stack) return 1;
    int tid = thread_create(work, (void *)42, stack, 65536);
    if (tid < 0) { free(stack); return 1; }
    if (thread_join(tid, 0)) return 1;
    free(stack);
    printf("result=%u\n", result);
    return 0;
}
```

## Реализация и проверка

Ядро по-прежнему сериализовано общей блокировкой; пользовательские потоки
работают параллельно с общим CR3. Удаление/замена пользовательского отображения
синхронно сбрасывает удалённые TLB до повторного использования физической
страницы. Запрос обслуживается также при ожидании общей блокировки ядра.
Не удаляйте отображения буферов/мьютексов, пока другой поток использует их
или выполняет с ними блокирующий системный вызов.

`make threadtest` использует отдельный `build/thread-base.img` и временные копии,
не изменяя основной `disk.img`. Проверяются 1, 2, 4, 8 CPU и ACPI fallback:
100 потоков без yield, отсутствие голодания, учёт CPU, FPU, общая память и FD,
мьютекс, malloc, join, повторное использование более 256 TID, удалённый TLB,
выход/kill процесса с потоками и существующий процессный тест `smpcheck`.
Результаты — `build/thread-*.log`. Проверка в QEMU не заменяет аппаратную.
