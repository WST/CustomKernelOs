# Многоядерное выполнение

MyOS запускает до **8 логических CPU** и распределяет пользовательские процессы
между ними. Это включает логические процессоры SMT, если прошивка публикует их
в таблице ACPI MADT. Каждый процесс закрепляется за CPU при создании; `exec`
сохраняет CPU, `fork` распределяет потомка независимо от родителя.

```
make run QEMU_CPUS=4
make run QEMU_CPUS=1
```

По умолчанию `make run` использует 4 CPU. При загрузке появляется строка
`SMP: 4 CPUs online`. Команда `sysinfo` показывает фактическое число запущенных
CPU, отдельно от количества логических CPU, сообщаемого CPUID.

## Устройство

* Обнаружение через RSDP/RSDT/MADT с проверкой контрольных сумм и границ таблиц.
* Запуск AP через xAPIC INIT/SIPI и trampoline по физическому адресу `0x7000`.
  Trampoline и mailbox находятся в уже зарезервированном первом MiB.
* У каждого CPU отдельные GDT, TSS, текущая задача, idle-контекст, квант
  планировщика и глубина IRQ. Адрес текущего каталога берётся из локального CR3.
  Сегмент GS (селектор 0x30) даёт доступ к номеру CPU без повторных CPUID.
* Внешние IRQ остаются на загрузочном CPU через PIC. PIT 100 Гц посылает
  остальным CPU scheduler IPI; отдельный APIC-таймер пока не используется.
  При пробуждении задачи её простаивающий CPU получает отдельный reschedule
  IPI немедленно; ожидание следующего тика PIT не требуется.
* Пользовательский код работает параллельно. Ядро защищено общей атомарной
  блокировкой (big kernel lock), захватываемой на входе и освобождаемой при
  возврате в ring 3 или ожидании idle. Потоки ядра исполняются на BSP.
* При захвате блокировки проверяется поколение отображений ядра. Локальный TLB
  сбрасывается только после изменения общих отображений, а не при каждом
  системном вызове. Пользовательские каталоги
  не исполняются одновременно на нескольких CPU: процессы не мигрируют,
  пользовательских потоков с общим CR3 пока нет. Удалённый `kill` выполняется
  отложенно, чтобы не освободить память ещё работающего процесса.

Без подходящей MADT, APIC/MSR или CPUID система продолжает работать на одном
CPU. При тайм-ауте запуска AP остаются уже запущенные CPU. x2APIC, hotplug CPU,
миграция задач, балансировка по нагрузке и параллельное выполнение ядра пока
не реализованы. Аппаратная проверка на реальных многоядерных ПК не выполнена.

## Производительность

Ускорение ожидается для нескольких вычислительных процессов, например нескольких
копий `primes` или `fputest`. Однопоточная программа не разделяется автоматически
между ядрами. Дисковые операции, системные вызовы и обработчики ядра по-прежнему
сериализованы. Закрепление процессов без балансировки может давать неравномерную
нагрузку. Ускорение в QEMU зависит от выбранного ускорителя и настроек TCG.

Исправление задержек GUI от 9 ноября 2026: частые CPUID заменены на GS,
безусловные перезагрузки CR3 — на проверку поколения, пробуждение удалённой
idle-задачи — на адресный IPI. В одном сравнительном запуске QEMU TCG с 4 CPU
100 000 `getpid` заняли около 470 мс до исправления и 90 мс после; 100 обменов
сообщениями между процессами — 1620 мс и 10 мс соответственно. Это микротесты,
а не измерение FPS рабочего стола; часы гостя имеют шаг 10 мс.

`make smptest` сохраняет результаты этих микротестов в общих SMP-логах.

## Проверка

```
make smptest
make test
make build/hardware/kernel.bin
```

`smptest` использует отдельный `build/smp-base.img`, а каждый запуск QEMU — его
временную копию. Основной `disk.img` не изменяется. Проверяются 1, 2, 4 и 8 CPU,
а также возврат к одному CPU при отключённой ACPI. Восемь ring-3 процессов
проверяют физические APIC ID, сохранность FPU, собственную память, файлы,
каналы и `waitpid`; отдельно проверяется завершение вычислительных процессов
с других CPU. Логи сохраняются в `build/smp-*.log`.
