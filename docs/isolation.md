# Изоляция процессов, IPC и защита стеков

## Управление процессами

Пользовательский `kill` разрешён самому процессу, авторизованным процессам того же
эффективного UID и авторизованному root. Потоки ядра через этот syscall не убиваются.
TID нормализуется до процесса-владельца, поэтому через ID потока нельзя обойти проверку.
Родство само по себе не разрешает убивать потомка, сменившего UID. Внутренние операции
ядра по завершению групп сохраняются для Ctrl+C, служб и обработки исключений.
Неавторизованный процесс не получает права root из-за нулевого поля UID.

## Общая память

`shm_alloc` создаёт объект, закрытый для других процессов, включая процессы того же
UID и root. Создатель привязан к PID, UID, признаку авторизации и поколению личности.
Разрешение на подключение выдаёт создатель конкретному живому процессу:

```c
int id = shm_alloc(4096);
void *data = shm_map(id);
shm_grant(id, receiver_pid, SHM_READ);             /* только чтение */
shm_grant(id, receiver_pid, SHM_READ | SHM_WRITE); /* чтение и запись */
shm_grant(id, receiver_pid, 0);                    /* запрет новых подключений */
```

Разрешение запоминает текущую личность получателя. После exec, входа/выхода из
аккаунта или смены UID старое разрешение не даёт подключиться новому контексту.
Read-only обеспечивается таблицами страниц. `mmap/mprotect` не меняют окно SHM.
Получатель не может выдать себе или другому процессу дополнительные права.

Отзыв разрешения запрещает новые подключения: уже отображённая память остаётся
полученной возможностью до `shm_unmap`, exec или завершения процесса. Это также
относится к уже отображённым буферам после смены UID. Fork, как и раньше, не
наследует SHM-отображения; их нужно явно разрешить потомку и подключить заново.

`shm_size(id)` возвращает размер в страницах (байтах, округлённых вверх) только
создателю или разрешённому/уже подключённому процессу. Последнее отключение
уничтожает объект. Неотображённую аллокацию можно освободить через `shm_discard`;
при сборке завершившегося процесса его неиспользованные объекты также освобождаются.
Повторно использованный слот получает новый ID: старый ID не открывает новый объект.
Лимиты: 64 объекта, до 16 МиБ каждый, 16 отображений на процесс и 16 получателей
разрешений на объект. SHM-стек нельзя отключить, пока использующий его поток не собран.

Оконная библиотека выдаёт рабочему столу разрешение на каждый создаваемый буфер
и новый буфер при resize. Desktop проверяет доступный размер перед чтением пикселей.
Старые GUI-программы необходимо пересобрать с новой оконной библиотекой.

## Сообщения и имена служб

Сообщения разрешены внутри процесса и между авторизованными процессами одного UID.
Для чужого UID получатель заранее разрешает отправителя: `msg_allow(pid, 1)`;
`msg_allow(pid, 0)` отзывает это исключение. Это не запрет обычного обмена одного UID.
Смена личности и exec сбрасывают свою очередь/разрешения и делают прежние разрешения
других получателей на этого отправителя недействительными. Ящик принадлежит процессу
и разделяется потоками. Поле `msg.from` всегда заполняет ядро PID процесса, а не TID
и не значением из пользовательского сообщения.

Имена служб ищутся внутри текущего авторизованного UID; чужое одноимённое объявление
не перехватывает поиск. При смене UID процессом его объявление следует за текущей
личностью владельца — это нужно экрану входа desktop. До авторизации регистрация
доступна только для `desktop` процессу, который уже владеет framebuffer; чужие
неавторизованные процессы не находят это объявление и не получают доступ к его IPC.
Для явных разрешений сообщений используются те же PID/UID/поколения, что и для SHM.

## Карта памяти и стеки

Размер основного стека — 1 МиБ, начало `0xBFF00000`. Страница
`0xBFEFF000..0xBFEFFFFF` не отображается и отделяет его от mmap. `MMAP_END` —
`0xBFEFF000`, верхняя граница не включается. Все границы заданы вместе в paging.h;
загрузчик ELF использует те же определения. mmap/munmap/mprotect не затрагивают
основной стек или его защитную страницу.

`thread_create` сохраняет передачу буфера вызывающей программой. Минимум теперь
12 КиБ, максимум 1 МиБ, рекомендуется 64 КиБ. Первая полная страница внутри буфера
становится недоступной из ring 3; префикс до неё не используется. Полезный стек
уменьшается на 4–8 КиБ. Защита не затрагивает соседние malloc-блоки, физическая
страница остаётся закреплённой. После успешного join доступ восстанавливается,
и буфер можно полностью использовать или освободить.

Пока поток существует, включая ожидание join после завершения, нельзя создать
перекрывающийся стек или снять/изменить отображения его буфера через munmap/mprotect.
Уменьшение кучи через sbrk также не может пересечь активный стек.
Проверка выполняется до изменения страниц. Прямое обращение к защитной странице
вызывает обычное завершение процесса с кодом 139; системный вызов с таким буфером
возвращает EFAULT. Защитные отображения восстанавливаются при сборке потока после
остановки использовавшего их CPU.

## Проверки

`make isolationtest` запускает отдельные диски QEMU на 1 и 4 CPU: чужие UID/PID/TID,
root и обычный пользователь, SHM grants/read-only/отзыв/exec, сообщения, подмена from,
пространства имён, очистка объектов, устаревшие ID, границы mmap, настоящие обращения
к guard-страницам, запрет их восстановления и повторное использование стека после join.
Ожидаемые segmentation fault в этих тестах проверяют защиту; PANIC не ожидается.
`make threadtest` проверяет 100 потоков на 1/2/4/8 CPU и ACPI fallback.
Оконный протокол проверяется launchtest и terminalwindowtest. Проверки используют
временные образы и не меняют рабочий disk.img. Квоты памяти/CPU и полноценные POSIX
сигналы не входят в эту реализацию.
